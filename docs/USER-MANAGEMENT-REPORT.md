## 2. ربط المستخدم بالمحل (بلا نظام مستخدمين منفصل)

- المستخدم يُنشأ في جدول `users`، وربطه بالمحل يتم عبر `project_memberships` (عضوية واحدة نشطة لكل مستخدم داخل محل واحد).
- **كل** طلب محمي يمرّ بـ `authMiddleware`: يستخرج التوكن ← المستخدم ← العضوية ← المشروع، ثم يفحص حالة العضوية (`active` فقط) قبل أي تنفيذ.
- كل استعلام في المسارات مقيّد بـ `project_id` الخاص بعضوية الطالب، فلا يمكن قراءة أو تعديل بيانات محل آخر حتى بتوكن صحيح.
- العمليات المالية المسجّلة حديثًا تحمل `created_by` = معرّف المنفّذ الفعلي؛ والسجلات القديمة **لم تُنسب** لأي مستخدم بلا دليل.

**قواعد ثابتة مُنفَّذة على الخادم:**
1. صلاحيات صاحب المحل كاملة دائمًا (21/21) ولا يمكن تقليصها.
2. المدير لا يمنح نفسه أو غيره أكثر من سقفه، ولا ينشئ مديرًا أو صاحب محل.
3. الموظف لا يتجاوز سقف `EMPLOYEE_MAX_PERMISSIONS` — أي طلب زائد **يُقصّ** ويُسجَّل كـ `PERMISSION_ESCALATION_BLOCKED`.
4. الموافقة على الطلبات حصرية لصاحب المحل (`requireOwner`).

## 4. آلية الاعتماد

1. صاحب المحل ينشئ حسابًا ← الحالة `active` فورًا.
2. المدير ينشئ حسابًا ← الحالة `pending` + صلاحيات **مقترحة** غير مفعّلة، والحساب لا يستطيع الدخول.
3. الطلب يظهر لصاحب المحل في الشاشة 38 مع الصلاحيات المقترحة.
4. صاحب المحل يوافق ← الحالة `active`، تُفعّل الصلاحيات المقترحة (بعد قصّها للسقف)، ويُسجَّل `APPROVE_ACCOUNT` + `PERMISSION_CHANGE`.
5. أو يرفض ← الحالة `rejected`، ويبقى الحساب ممنوعًا من الدخول، ويُسجَّل `REJECT_ACCOUNT_REQUEST` مع سبب الرفض.
6. المدير **لا يستطيع** الاعتماد ولا تفعيل حسابه بنفسه — كل المحاولات تُرفض بـ 403 وتُسجَّل.

## 5. آلية التعطيل وإعادة التفعيل والحذف

- **التعطيل هو الإجراء الافتراضي** (لا حذف): الحالة `disabled` + **حذف كل توكنات المستخدم** (خروج فوري) + بقاء كل السجلات والعمليات.
- المدير **يطلب** التعطيل/الحذف/إعادة التفعيل فقط؛ التنفيذ المباشر لصاحب المحل وحده (`requireOwner`).
- عند التعطيل يُغلق طلب المدير المعلّق تلقائيًا بحالة `cancelled` مع ملاحظة «نُفِّذ مباشرة بواسطة صاحب المحل».
- **إعادة التفعيل** تعيد **نفس** الصلاحيات المعتمدة سابقًا — لا تمنح صلاحيات جديدة.
- **الحذف** = حذف منطقي: الحالة `deleted` + تعمية كلمة المرور + إبطال الجلسات + **بقاء صف المستخدم وكل عملياته** (حتى لا تنكسر مراجع `created_by`).
- الواجهة تشرح الفرق بين التعطيل والحذف وتطلب **تأكيدًا مزدوجًا** قبل التنفيذ، وتعرض سجل نشاط المستخدم.

## 7. المحدوديات المعلنة (بصراحة)

1. **تعديل عملية مالية:** لا يوجد مسار `PUT /api/transactions/:id` في التطبيق أصلًا؛ لذلك صلاحية `edit_transaction` موجودة في المصفوفة ومحجوبة عن المدير/الموظف، لكن لا توجد شاشة أو مسار لتعديل عملية. **لم أضف ميزة جديدة غير مطلوبة.**
2. **إعادة تعيين كلمة المرور:** لا يستطيع صاحب المحل ولا المدير رؤية كلمة مرور أي مستخدم؛ التغيير الذاتي عبر الشاشة 12، والنسيان عبر مسار استعادة الحساب القائم (SMS/بريد). «إعادة تعيين إجبارية من صاحب المحل» ليست ضمن النطاق الحالي.
3. **عزل الحساب الواحد:** `users.phone` فريد عالميًا، لذا لكل شخص عضوية نشطة واحدة داخل محل واحد. دعم شخص في أكثر من محل يحتاج قرارًا منفصلًا.
4. **حدّ محاولات الدخول (Rate limit):** غير موجود على تسجيل الدخول (موجود لاستعادة الحساب فقط). أوصي بإضافته.
5. **حصانة سجل التدقيق:** محمي على مستوى الـAPI (لا مسار للتعديل أو الحذف — تم اختباره)، لكن لم تُضف triggers على مستوى قاعدة البيانات.
6. **بيانات الإنتاج:** لم أُجرِ أي مقارنة «قبل/بعد» على مجموعة البيانات الحقيقية (نسخة ما قبل العمل كانت غير مكتملة)؛ كل مقارنات السلامة أُجريت على قاعدة اختبار مؤقتة مع سيناريوهات مطابقة.
