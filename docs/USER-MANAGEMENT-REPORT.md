## 2. ربط المستخدم بالمحل (بلا نظام مستخدمين منفصل)

- المستخدم يُنشأ مرة واحدة في جدول `users`، وربطه بكل محل عبر `project_memberships` (**عضوية واحدة لكل محل** — يمكن للشخص الواحد أن يكون عضوًا نشطًا في أكثر من محل بحساب واحد ونفس كلمة المرور).
- **كل** طلب محمي يمرّ بـ `authMiddleware`: يستخرج التوكن ← المستخدم ← العضوية ← المشروع، ثم يفحص حالة العضوية (`active` فقط) قبل أي تنفيذ.
- كل استعلام في المسارات مقيّد بـ `project_id` الخاص بعضوية الطالب، فلا يمكن قراءة أو تعديل بيانات محل آخر حتى بتوكن صحيح.
- العمليات المالية المسجّلة حديثًا تحمل `created_by` = معرّف المنفّذ الفعلي؛ والسجلات القديمة **لم تُنسب** لأي مستخدم بلا دليل.

---

### 2.1 تعدد المحلات (حساب واحد ← أكثر من محل)

- إضافة شخص موجود بالفعل (نفس رقم الهاتف) إلى محل آخر: `POST /api/accounts` ينشئ **عضوية جديدة** على نفس الحساب بلا كلمة مرور جديدة (`existing_account: true`)، ويُسجَّل `LINK_EXISTING_ACCOUNT` + إشعار `ACCOUNT_LINKED`. التكرار في **نفس** المحل يُرفض بـ 409 `ALREADY_MEMBER`.
- الدخول: إذا كان للحساب أكثر من عضوية نشطة، يُعاد `requires_project_selection: true` + قائمة المحلات **بلا توكن**، ثم يُصدر التوكن بعد اختيار `projectId`. التوكن مربوط بمحل واحد، وعزل البيانات يبقى كما هو.
- `GET /api/auth/my-projects` يعرض محلات المستخدم ودوره وحالته في كل محل.
- `POST /api/auth/switch-project` يصدر توكنًا جديدًا للمحل الآخر بصلاحياته وسجله في التدقيق (`SWITCH_PROJECT`).
- `POST /api/auth/leave-project` يجعل العضوية `left` («غادر المحل») ويحذف توكنات ذلك المحل فقط؛ **صاحب المحل لا يستطيع مغادرة محله** (400)، وكل سجلاته التاريخية تبقى عند المحل.

### 2.2 إعادة تعيين كلمة المرور الإجبارية (صاحب المحل)

- صاحب المحل فقط (`requireOwner`) يعيد تعيين كلمة مرور موظف/مدير داخل **محله**: تُولَّد كلمة مرور مؤقتة تُعرض **مرة واحدة**، تُخزَّن كبصمة scrypt فقط، وتُبطَل كل جلسات المستخدم.
- بعد الدخول، `must_change_password = 1` يجعل **كل** المسارات المحمية ترد **428 `PASSWORD_CHANGE_REQUIRED`** (عدا `/api/auth/me` وتغيير كلمة المرور والخروج)، والواجهة تُلزمه بالشاشة 12 قبل أي شيء آخر.

### 2.3 حدّ محاولات الدخول

- 5 محاولات فاشلة / 15 دقيقة لكل (`المُعرِّف` أو IP) ← قفل 15 دقيقة ← **429 `TOO_MANY_ATTEMPTS`** مع `retry_after_seconds`، وكل حالة فاشلة تعيد `remaining_attempts`، والحدث مسجَّل `LOGIN_THROTTLED`. نجاح الدخول يصفّر العدّاد.

## 4. آلية الاعتماد

1. صاحب المحل ينشئ حسابًا ← الحالة `active` فورًا.
2. المدير ينشئ حسابًا ← الحالة `pending` + صلاحيات **مقترحة** غير مفعّلة، والحساب لا يستطيع الدخول.
3. الطلب يظهر لصاحب المحل في الشاشة 38 مع الصلاحيات المقترحة.
4. صاحب المحل يوافق ← الحالة `active`، تُفعّل الصلاحيات المقترحة (بعد قصّها للسقف)، ويُسجَّل `APPROVE_ACCOUNT` + `PERMISSION_CHANGE`.
5. أو يرفض ← الحالة `rejected`، ويبقى الحساب ممنوعًا من الدخول، ويُسجَّل `REJECT_ACCOUNT_REQUEST` مع سبب الرفض.
6. المدير **لا يستطيع** الاعتماد ولا تفعيل حسابه بنفسه — كل المحاولات تُرفض بـ 403 وتُسجَّل.

## 5. آلية التعطيل وإعادة التفعيل والحذف

- **التعطيل هو الإجراء الافتراضي** (لا حذف): الحالة `disabled` + **حذف كل توكنات المستخدم** (خروج فوري) + بقاء كل السجلات والعمليات.
- المدير **يطلب** التعطيل/الحذف/إعادة التفعيل فقط؛ التنفيذ المباشر لصاحب المحل وحده (`requireOwner`).
- عند التعطيل يُغلق طلب المدير المعلّق تلقائيًا بحالة `cancelled` مع ملاحظة «نُفِّذ مباشرة بواسطة صاحب المحل».
- **إعادة التفعيل** تعيد **نفس** الصلاحيات المعتمدة سابقًا — لا تمنح صلاحيات جديدة.
- **الحذف** = حذف منطقي: الحالة `deleted` + تعمية كلمة المرور + إبطال الجلسات + **بقاء صف المستخدم وكل عملياته** (حتى لا تنكسر مراجع `created_by`).
- الواجهة تشرح الفرق بين التعطيل والحذف وتطلب **تأكيدًا مزدوجًا** قبل التنفيذ، وتعرض سجل نشاط المستخدم.

### تفصيل المحدودية #6 (البيانات الحقيقية)

العينة: `tests/fixtures/real-dataset-pre-usermgmt.db` (بصمة SHA-256 مثبّتة داخل الاختبار) — وهي قاعدة الإنتاج كما كانت **قبل** نظام إدارة المستخدمين: 3 عملاء، 3 عمليات، محلان، مستخدمان، 12 سجل تدقيق.

ما يثبته الاختبار فعليًا:
- **تساوي حرفي:** صفوف العملاء والعمليات والمشاريع والعضويات متطابقة حقلًا بحقل قبل/بعد الترحيل، وعدد الصفوف لم يتغيّر.
- **الأرصدة:** لكل عميل، ولكل محل، وللمجاميع (مدفوعات/مسحوبات/عدد العمليات/صافي) — متطابقة تمامًا، ثم مطابقة مرة أخرى بأرقام الـAPI الحقيقي (`/api/customers`, `/api/transactions`, `/api/reports/summary`).
- **لا نسبة بلا دليل:** `created_by` للعمليات القديمة كما هو، والأعمدة المضافة `customers.created_by/updated_by` بقيت `NULL` لكل الصفوف القديمة.
- **لا إعادة كتابة اعتماد:** بصمات `password_hash` القديمة لم تُلمس.
- **الفواتير:** كل عملية نشطة ما زالت مرتبطة بعميل موجود، بلا تكرار في المعرّفات ⇒ الفواتير المولّدة من نفس البيانات لا تتغيّر.
- **التغيير الوحيد المقصود:** ترقية شيفرات الصلاحيات القديمة (`add_customers`, `manage_employees` …) إلى المصفوفة الجديدة (21 صلاحية) + عمود `must_change_password` بقيمة آمنة (0) — دون المساس بأي بيانات تشغيلية.
- **العزل:** المحل الثاني لا يرى أي بيانات من المحل الأول.

### ما بقي خارج النطاق (ليس محدودية، بل قرار نطاق)
- تعديل عملية مالية متاح لصاحب المحل فقط؛ المدير/الموظف محجوبان دائمًا (بحسب المصفوفة).
- سجل التدقيق غير قابل للتعديل أو الحذف إطلاقًا — لا توجد «إدارة سجل» ولا تنظيف تلقائي (وهذا مقصود).
- البيانات القديمة تبقى بلا نسبة إلى مستخدم حتى يوجد دليل — لا تُنسب تلقائيًا أبدًا.
